# 녹음 코어 안정화 감사

## 목표

일반 녹음, 선물 녹음, 음성 쪽지가 동일한 녹음 상태 규칙과 오디오 자원 수명주기를 사용하도록 점진적으로 통합한다. 기존 녹음 데이터와 API 형식은 마이그레이션이 끝날 때까지 유지한다.

## 감사 당시 확인된 위험

1. 일반 녹음과 선물 녹음의 캡처 방식이 다르다.
   - 일반 녹음은 긴 원본과 절 경계를 함께 관리한 뒤 잘라 저장한다.
   - 선물 녹음은 절마다 `MediaRecorder`를 정지하고 다음 recorder를 즉시 만든다.
   - 같은 버튼 이름이라도 정지, 저장, 다음 절의 의미와 실패 경로가 다르다.
2. UI 상태가 독립 불리언으로 분산돼 있다.
   - `recording`, `savingRecording`, `requestingMic`, `advancingRef` 등이 조합된다.
   - 불가능한 조합을 타입이나 단일 전이 규칙으로 막지 못한다.
3. 오디오 자원 소유권이 여러 컴포넌트에 흩어져 있다.
   - `MediaStream`, `MediaRecorder`, `AudioContext`, object URL, BGM audio를 각 화면이 직접 정리한다.
   - 중복 stop/close, 언마운트 중 콜백, 이전 세션 콜백이 새 UI를 갱신할 위험이 있다.
4. 선물 녹음은 화면을 먼저 다음 절로 이동한 뒤 이전 절 업로드를 완료한다.
   - 업로드 실패 시 화면 위치와 서버 저장 상태가 갈라질 수 있다.
   - 마지막 절과 중간 절이 서로 다른 대기 동작을 보인다.
5. 일부 회귀 테스트는 렌더링된 동작이 아닌 소스 문자열을 확인한다.
   - 버튼 존재는 잡지만 실제 상태 전이, 중복 클릭, 비동기 실패는 보장하지 못한다.

## 목표 상태 전이

`idle → requesting-permission → recording → stopping → saving → ready`

실패는 `error`로 모으고, 명시적인 `RETRY` 또는 `RESET`만 다음 시도를 허용한다. 정지·저장 중 중복 입력은 무시한다.

## DB 감사 결과

### DB에 유지할 영속 사실

- `recordings`: 소유자, 말씀 위치, R2 object key, MIME, 크기, 길이, BGM과 생성 시각
- `recording_group_id`, `recording_mode`: 연속 녹음에서 생성된 절들을 추적하는 출처 메타데이터
- `gift_draft_items`: 선물에 포함할 말씀 위치와 원본 녹음 참조 또는 별도 R2 object key
- `gifts`, `gift_recordings`: 전송 시점의 불변 선물 스냅샷과 수신자별 열람 상태

### DB에 추가하지 않을 일시 상태

- 마이크 권한 요청 중
- 녹음 중
- 정지 처리 중
- 업로드/저장 중
- 현재 선택된 절과 다음 절
- 재생·일시정지·BGM 미리듣기 상태

이 값들은 브라우저 세션의 공통 상태 머신 또는 저장된 절 목록에서 파생한다. 새 status 컬럼이나 별도 녹음 세션 테이블은 만들지 않는다.

### 이미 파생되고 있는 값

- 선물 초안의 `recorded`, `recorded count`, `nextPosition`, `sendable`은 `object_key` 또는 `source_recording_id`에서 계산된다.
- 이 값들은 현재 DB 컬럼이 아니므로 그대로 유지한다.

### 로컬 DB 정리에서 제거한 중복

- `gifts.recording_count`, `gifts.total_size_bytes`는 제거하고 `gift_recordings`에서 조회할 때 계산한다.
- `gift_drafts.recipient_key`는 기존 단일 수신자 값을 `recipient_keys_json`으로 보정한 뒤 제거한다.
- 선물 초안의 대표 수신자와 수신자 수는 `recipient_keys_json`의 첫 항목과 배열 길이에서 파생한다.

이 변경은 아직 로컬에만 있으며 배포 DB에는 적용하지 않았다. 메모리 SQLite에서 단일·복수 수신자와 선물 집계 보존을 검증한 후 전체 회귀 테스트를 통과해야 한다.

### 이번 통합에서 건드리지 않을 값

- `user_states.state_json`은 여정 설정을 저장하며 오디오 캡처 상태의 source of truth로 사용하지 않는다.

### 결론

녹음 상태 통일을 위해 필요한 DB 마이그레이션은 없다. DB는 저장 완료된 결과만 소유하고, 진행 중 상태는 공통 클라이언트 상태 머신 하나만 소유한다.

## 점진적 변경 순서

1. [완료] 순수 상태 머신으로 허용되는 전이를 고정한다.
2. [완료] 공통 녹음 세션이 stream, recorder, context의 생성과 단 한 번의 정리를 소유하게 한다.
3. [완료] 일반 녹음에 상태 머신을 연결하되 저장/API 로직은 유지한다.
4. [완료] 선물 녹음을 같은 세션으로 옮기고, 현재 절 저장 성공 뒤에만 다음 절을 시작한다.
5. [완료] 음성 쪽지도 같은 세션을 사용한다.
6. [대기] 실제 브라우저에서 권한 거절, 중간 종료, 연속 절 이동, 마지막 절 저장, 업로드 실패·재시도, 재생을 검증한다.

## 구현된 공통 계약

- `lib/recording-machine.ts`는 허용되는 녹음 상태 전이만 담당하는 순수 로직이다.
- `lib/recording-session.ts`는 마이크 스트림, 오디오 그래프, recorder, chunk, 캡처 시간을 한 곳에서 소유한다.
- 일반 녹음, 선물 녹음, 음성 쪽지는 `createRecordingSession`만 호출한다. 화면에서 `new MediaRecorder` 또는 오디오 그래프를 직접 만들지 않는다.
- `stop()`은 중복 호출돼도 같은 종료 결과를 반환하고, `dispose()`는 결과를 버리면서 자원을 한 번만 정리한다.
- 선물 녹음은 낙관적 다음 절 상태와 별도 업로드 큐를 제거했다. 캡처한 현재 절을 저장하고 서버 초안을 다시 조회한 후에만 다음 세션을 시작한다.
- DB에는 저장 완료 사실만 남긴다. 화면의 녹음 단계와 저장 로딩 상태를 표현하기 위한 컬럼은 추가하지 않았다.

## 배포 기준

- 단위·통합·UI 회귀 테스트가 모두 통과한다.
- 기존 저장 녹음과 선물 초안을 재생할 수 있다.
- 모바일 실제 녹음에서 절 이동과 마지막 저장이 성공한다.
- 사용자의 별도 배포 승인이 있다.
