# 녹음 실패·불러오기 실패 조사 보고

작성일: 2026-09-08

## 먼저 결론

과거 아이폰 오류를 하나의 원인으로 확정할 자료는 아직 없습니다. 운영 서버 로그를 최근 3시간 범위에서 오류만 조회하고 전체 요청으로 넓혀 조회했지만, 반환된 기록이 없었습니다. 이것은 오류가 없었다는 뜻이 아닙니다. 브라우저에서 일어난 오류는 기존 코드가 원인 정보를 남기지 않았습니다.

코드 조사와 재현 테스트에서는 **기기 저장소가 한 번 열리지 않으면 같은 화면에서 재시도해도 계속 실패할 수 있는 문제**를 확인하고 수정했습니다. 다음 실패부터는 어디에서 왜 실패했는지 구분할 수 있도록 진단 기록을 추가했습니다.

## 확인한 문제와 조치

| 확인한 문제 | 쉽게 설명하면 | 조치 |
| --- | --- | --- |
| 기기 저장소 열기 실패 결과를 계속 재사용 | 문이 한 번 안 열렸다고 다음에도 문을 두드리지 않는 상태 | 열기 실패 결과를 비워 다음 시도에서 다시 열도록 수정. 재시도 때 실제로 두 번째 열기 요청이 발생하는 테스트 통과 |
| 마이크 오류를 같은 안내로 표시 | 권한 거부인지, 사용할 마이크가 없는지, 기기가 사용 중인지 구분할 기록이 없음 | 마이크 요청, 오디오 엔진 생성, 녹음기 생성·시작·녹음 중 오류를 별도 단계로 기록 |
| 연속 녹음기의 비동기 오류를 즉시 기록하지 않음 | 녹음 중 인코더 오류가 나도 나중에 절을 넘기거나 멈출 때까지 원인을 놓칠 수 있음 | 오류 발생 순간 기록. 결과 Promise에 즉시 오류 관찰자를 연결하되, 원래 실패는 호출자에게 그대로 전달 |
| 보관함 요청의 HTTP 상태를 버림 | 로그인 만료와 서버 장애가 같은 ‘불러오기 실패’로 보임 | HTTP 상태와 서버 요청 번호를 보관 |
| 음성 플레이어의 로딩 오류 처리 부재 | 파일이 없거나 형식을 읽지 못해도 무엇이 실패했는지 남지 않음 | 음성 파일 오류 번호, 준비 상태, 네트워크 상태 기록. 한 절 듣기의 재생 거부도 기록 |
| 서버 저장·읽기 오류의 단계 구분 부족 | DB 목록이 없는지 실제 음성 파일이 없는지 구분하기 어려움 | 인증, DB 준비·조회·쓰기, 업로드 본문, 파일 저장·조회 단계와 상태·요청 번호 기록 |

첫 번째 문제는 반복 실패를 만드는 **확인된 코드 결함**입니다. 사용자의 과거 오류가 그 결함 때문에 발생했다고까지 확정한 것은 아닙니다.

## 다음 오류를 어떻게 판단하는가

- `microphone / NotAllowedError`: 마이크 권한 또는 브라우저 보안 정책에 의해 거부됨.
- `microphone / NotFoundError`: 조건에 맞는 입력 장치를 찾지 못함.
- `microphone / NotReadableError`: 장치는 있지만 브라우저·OS가 열지 못함. 다른 앱 사용, 장치 오류 등은 추가 확인 필요.
- `local-save / QuotaExceededError`: 기기 저장 공간 한도 때문에 저장 실패.
- `upload / 401`: 업로드 요청의 인증 실패. 로그인 만료인지 다른 인증 문제인지 추가 확인.
- `upload / 413`: 서버의 녹음 크기 제한 초과. 현재 제한은 25MB.
- `audio-load / mediaCode 2`: 미디어 네트워크 오류.
- `audio-load / mediaCode 3`: 음성 디코딩 실패.
- `audio-load / mediaCode 4`: 재생할 수 있는 소스를 확보하지 못함. 404 응답도 이 번호로 나타날 수 있으므로 **파일 손상이라고 단정하지 않음**.
- 서버 `object-missing`: 녹음 정보는 찾았지만 실제 음성 파일이 없음.
- 서버 `metadata-missing-or-inaccessible`: 녹음 정보가 없거나 접근할 수 없음. 개인정보 보호를 위해 외부 응답에서는 둘을 구분하지 않음.
- `audio-play / AbortError`: 재생 도중 정지·다른 재생 요청으로 중단될 수 있음. 저장된 파일 손상 증거가 아님.

오류 이름의 의미는 [MDN getUserMedia 문서](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), 미디어 오류 번호는 [MDN MediaError 문서](https://developer.mozilla.org/en-US/docs/Web/API/MediaError/code)를 기준으로 해석합니다.

## 어디에 기록하는가

1. 브라우저: `verse-recording-diagnostics` 키에 최근 50건을 보관합니다. 콘솔에서도 `recording_diagnostic`으로 확인할 수 있습니다.
2. 서버: 같은 사이트의 인증된 `/api/recording-diagnostics`로 전송하며 `recording_client_failure`로 기록합니다. 녹음 API 자체의 오류는 `recording_server_failure`로 기록합니다.
3. 요청을 연결할 때: 보관함·업로드 응답의 `X-Recording-Request-Id`를 클라이언트 로그에도 저장합니다. 미디어 요소 오류는 해당 헤더를 읽을 수 없어 서버 기록의 시간·단계를 함께 확인해야 합니다.

기록 내용은 단계, 오류 이름/번호, HTTP 상태, 파일 크기, 온라인 여부, 화면 숨김 여부, 브라우저 종류·버전, 요청 번호입니다. 원음, 성경 본문, 계정 ID, 주소, 원문 오류 메시지는 수집하지 않습니다. 동일 오류는 5초 이내 중복을 줄이고 클라이언트 전송은 분당 20건으로 제한합니다. 수집 API는 2KB 초과 본문과 비인증 요청을 거부합니다.

오프라인이거나 인증이 실패하면 서버 전송이 안 될 수 있습니다. 이때는 기기에 남은 기록으로 확인하며, 저장소 자체가 막히면 기기 기록도 남기지 못할 수 있습니다. 로그 전송 실패가 녹음을 중단시키지는 않습니다. 서버 로그 보존 기간은 호스팅 서비스 설정을 따릅니다.

## 검증 결과

- 단위·통합 테스트: 659개 통과.
- 모바일 Chrome·WebKit에서 목록 401, 음성 파일 404를 실제로 발생시킨 UI 테스트: 4개 통과.
- 목록 실패 로그가 서버 수집 API에 도착해 204 응답을 받는 것 확인.
- 실제 미디어 요소가 404를 미디어 오류 4번으로 기록하는 것 확인.
- 민감한 임의 문자열을 로그에서 제거하는 검사, 로그 중복·빈도 제한, 진단 API 인증·본문 크기 제한 검사 통과.

실제 아이폰에서 새로 수집된 오류를 분석한 결과는 아직 아닙니다. 현재 보고는 코드 결함과 재현 시험 결과이며, 다음 실사용 오류 기록으로 원인을 더 좁힐 수 있습니다.
